# Strategy and simulation production branches

Use actual grid/hex, footprint, selection, zoom and interaction contracts. Art bounds, overhang and navigation footprint are different data. The following studies create visual assets and assembly evidence, not working economy/pathfinding/game rules.

## Real-time strategy (RTS)

Build three supplied functions as different roof/mass silhouettes before team color: for example a storage volume, production structure and observation structure if those functions exist. Add neutral, team and damaged states with identical footprint/anchor. Place unit-size proxies around entrances and rally/service side; keep animated appendage envelopes separate from occupied tiles. Reserve a broad team-color panel rather than tinting every material.

Render near/far and selected/unselected with a grayscale version and UI overlays. If function survives only a tiny sign, alter the large roof/functional shape. If team hue makes functions indistinguishable, reduce color area and restore value/mass separation. Deliver footprint/overhang/selection layers, state sheet and far-camera images; these do not prove unit navigation or production behavior.

## Turn-based strategy (square and hex)

Select actual grid coordinates, tile size, elevation steps and legal rotations. Build center, edge, corner and height-transition tiles plus one unit/structure occupancy study. Hex tiles need the exact orientation and neighbor offsets; a square-grid rotation recipe is not interchangeable. Keep terrain art irregularity inside agreed boundary/connection planes and label intentional overhangs.

Use subdued terrain values with distinct boundary/selection treatment supplied by UI, not permanent bright edges on all geometry. Inspect adjacent tile combinations, tall-object occlusion and far zoom from the actual projection. If a cliff decoration hides a selected cell, lower/reposition art or provide the approved cutaway variant. Deliver neighbor/rotation sheet and elevation sections; movement costs, range and turn rules require the target implementation.

## Tower defense

Model path, build pad, tower base and entrance/exit markers as distinct families. Use the supplied lane width and tower footprint; keep attack-range circles and enemy envelopes in diagnostic collections. Build tower upgrade stages with the same socket/pivot and identify barrel/rotor overhang at each stage. A tall upgraded tower must not accidentally cover an adjacent pad in the intended camera.

Separate route surface, buildable ground and decorative border by form/value as well as hue. Test a crowded tower cluster with effects disabled, then with worst-case supplied effect proxies. If paths resemble build pads, repair construction grammar; if towers hide enemies, adjust silhouette/height staging within approved bounds. Deliver upgrade states, pad/path join sheet and camera comparisons, with range, targeting and enemy flow explicitly untested.

## MOBA lanes and structures

Obtain lane/jungle/objective vocabulary and the actual camera/character scale. Build lane edge, vegetation/concealment family, tower/objective base and landmark as modular pieces. Keep function and faction identity separate and preserve consistent interaction footprint through active/damaged/destroyed states. Stage allied/enemy-size proxies on both approaches; reverse views matter even with a nominal fixed camera.

Reserve floor quietness around action; team colors belong in controlled zones and broad value contrast should keep units legible. If vegetation falsely implies guaranteed concealment, reconcile its art with the supplied visibility proxy and label the static scope. If tower rubble resembles live tower base, differentiate destroyed state shape. Deliver lane/jungle/objective state and far-camera sheets; navigation, fog-of-war and combat balance are not inferred from the layout.

## City builder

Choose lot/grid and road/service connector contracts. Build a representative residence, service and industrial function with front/back access, utility attachment and low/high-density state. Roofs and large functional parts must identify use at far zoom. Place building anchor and road connector independently when required; disclose roof/canopy overhang beyond the lot rather than silently clipping it.

Use regional material coherence while reserving service/state accents. Render joined lots, inside/outside road corners and crowded blocks from zoom extremes. If doors face inaccessible rear lots, fix connector orientation; if tall buildings hide required streets, provide approved cutaway/height alternatives rather than claiming pathfinding handles it. Deliver lot/connector data, density states and adjacent-block visual tests; service coverage, traffic and simulation performance need engine evidence.

## Colony simulation

Treat each workstation/room as a use sequence: approach, worker position, input storage, operating space and output/storage. Build furniture/equipment with occupied and idle state and a roof/wall cutaway strategy for the supplied camera. Keep bed/door/tool interactions aligned to the actual pawn size. Shelves/doors that animate need both open envelopes and collision intent identified.

Differentiate work, rest and storage by large forms, with modest material accents. If a roof makes activity invisible, implement the approved removable/cutaway art state. If workstation clutter fills the worker slot, move it before increasing the room size. Deliver interaction-marker and state sheet plus crowded-room review; scheduling, needs and job/economy behavior remain external.

## Life simulation

Build a domestic interaction set at the supplied body scale: seat/table/storage or requested equivalents, with sitting/standing/reach markers and open/closed states. Coordinate seat height, knee/arm clearance and door swing using actual proxies. Decorative bounds should not impersonate interaction bounds. Keep variants sharing attachment landmarks so recolors and upgrades do not shift hands/feet.

Use friendly or realistic style from the project, not a compulsory pastel palette. Inspect seated eye-level and actual game camera, including wall cutaway when needed. If a cabinet opens through a chair or users float above seats, repair pivot/marker geometry. Deliver interaction landmarks, state poses and assembly measurements; animation alignment and navigation still require runtime checks.

## Farming simulation

Choose plot dimensions, row direction and tool/harvest vocabulary. Build soil dry/wet/tilled states and at least seedling/growing/ready/harvested crop variants if those states exist. Keep root/pivot anchored to plot coordinates through growth; expanded foliage must have a declared overhang and avoid hiding neighboring readiness. Model irrigation/storage/tool access as separate assets with plausible junctions.

Use growth-state silhouette and value differences before reliance on color/glow. Test dense adjacent plots, target zoom and low-light collection view. If mature canopy conceals plot borders, group/lift/reduce leaves or adjust approved camera; if tools do not reach the row, repair owned dimensions/handles. Deliver state lineup, plot/irrigation connector sheet and harvest-proxy views; yield, timing and watering logic are unimplemented.

## Other simulation/process assets

For a requested simulation outside these families, decompose the visible process into input, storage, operation, output and service states before modeling. Record which dimensions and states come from the actual system and which are visual proposals. Build one representative loop and all transition geometry, including expanded/open bounds. Use clearly named source/state variants rather than embedding logic claims in model names.

Inspect actual actor/tool contact and final camera, with status colors disabled to ensure form still communicates use. A pipeline that appears connected needs connector measurement; a plausible machine cannot be called functional. Deliver process/state diagram, interface anchors and unresolved runtime tests. Do not invent unrelated economic rules to fill gaps.
