# Levels and encounters

## Level branch

Start with the intended experience and the player's current knowledge, tools and movement envelope. Obtain camera, scale, traversal limits and relevant objectives from project evidence. Unknown jump distance, clearance or character width remains a proposed blockout assumption, not engine-verified geometry.

Lay out routes, landmarks, sightlines, objectives, gates and checkpoints in a readable spatial description or diagram. For each important space, explain what the player should notice, choose or learn. Distinguish critical path, optional rewards and return paths. Check that a gate communicates its requirement and that failure or backtracking has an intentional cost.

Trace a first-time route and a knowledgeable route. Test whether the landmark is visible when needed, whether an alternate route bypasses a required teaching beat, and whether the return journey creates a new choice or only repetition. If movement defines reachability, specify the engine blockout checks needed; attractive concept art cannot prove a jump can be made.

## Encounter branch

Define purpose, entry conditions, arena/space, participating roles, win/failure/exit conditions, pacing and recovery. Explain how enemies, obstacles and interactables cooperate to create decisions. Use an encounter beat map where timing matters: introduction, pressure, opportunity and release should correspond to actual events rather than cinematic labels alone.

Walk the encounter from different legal starting positions and affected resource states. Check overlapping telegraphs, spawn visibility, escape space, camera occlusion and whether one threat removes the counterplay for another. Include player strategies the design intends to support; flag a dominant safe strategy as a hypothesis to observe, not a proven defect without play evidence.

For cooperative encounters, scale roles and shared information deliberately with player count. Consider a player joining late, becoming incapacitated or leaving only when the mode supports it. Define what resolves an encounter when one actor is removed and what prevents duplicate rewards.

## Onboarding branch

Choose what the player needs to infer at this moment. Present a safe or recoverable opportunity to notice and try the rule, then combine it with an existing skill before escalating pressure. Do not assume one text prompt establishes learning. For accessibility, account for the actual input method, reading conditions and cue channels affecting the lesson.

Specify the observable learning signal: predicting a hazard, using a new option without help, or explaining why an action failed. Record facilitator assistance during a test so coached success is not mistaken for discoverability. A puzzle's solution should not be explained to a participant before testing whether its cues are sufficient.

## Procedural branch

Define what can vary and what must remain true: connectivity, reachable goal, required key before locked gate, placement clearance, resource sufficiency and difficulty constraints as appropriate. Separate a solvability invariant from a desirable pacing property. Choose validation that fits the generator, including seed reproduction and failing-seed retention when generation is implemented.

Review combinations and extreme legal parameters, not only attractive samples. A disconnected critical path requires repair, rejection or regeneration according to an explicit policy. A connectivity graph does not prove physical traversability, puzzle correctness or visual clarity; name the next engine or playtest check.

## Deliverable

Return the map/beat description at the requested fidelity, a walkthrough, dependencies and acceptance scenarios. For asset production handoffs, include units, pivot/origin, modular joins, collision intent, camera distance and state readability only when known or proposed. Keep engine blockout acceptance, art review and player observations separate.
