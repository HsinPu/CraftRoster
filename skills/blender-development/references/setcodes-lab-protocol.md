# Optional Blender Lab transport and bounded smoke checks

First inspect the actual connected tool schemas and current file/scene. The source's Blender Lab connection is a distinct protocol, not a generic description of every Blender MCP. Installed Skill files establish neither a listening server nor authorization to change the user's global MCP config, enable extensions or online access. Prefer the existing functioning connector or the established background runner. Never probe an unrelated live scene by executing a destructive test.

For an explicitly chosen compatible Lab add-on, the inspected source sends UTF-8 JSON `{"type":"execute","code":"...","strict_json":false}` followed by a NUL byte to an explicit loopback host/port (source default 127.0.0.1:9876). It expects a NUL-terminated JSON response with `status`, dict `result` and optional stdout/error. A bridge's newline-delimited stdio JSON-RPC is a separate framing layer. Tool names such as blender_execute_python and blender_scene_info are source-specific. A server speaking another command envelope cannot be substituted merely because its port matches.

If implementing or manually diagnosing that adapter, require a compatible version/schema, positive finite timeout and bounded response size (for example 16 MiB for compact reports). Accumulate partial reads until one terminator; reject EOF before it, malformed JSON, non-dict envelopes or non-ok status. Treat extra frames explicitly rather than swallowing them. Keep logs on stderr for stdio MCP. Do not automatically retry an execution after a timeout: the main-thread bake/export may still be running and a retry can duplicate writes. Query the intended owned job's completion artifact before deciding recovery. A local socket is execution authority, not a sandbox; do not expose it externally or feed untrusted downloaded Python.

Concatenating a reviewed helper and job script is only appropriate when both are trusted local files and namespace behavior is known. The job should emit a small dict with source/output hashes and actual statuses. Long bakes block a live main thread; prefer an isolated background job when allowed. Save dirty owned state or refuse file replacement; never read_homefile on an unsaved/unowned scene. Background jobs have no window, and operators need an actual context or data-API equivalent. Shared material nodes, selection, modes and action state need snapshots and finally restoration.

## Compatibility smoke slice

Use a new isolated output directory and explicit executable. Discover Blender/Python/build/API first. Discover a separate host interpreter only if a host image tool is needed; hardcoded python3 can resolve differently on Windows or lack Pillow. No new dependency installation follows implicitly. Start a small synthetic house with a roof/trim and a rectangular 64x32 image; test blockout/UV, constant metallic=1 and linked metallic bake, optional ORM pack, selected-only GLB/FBX and a fresh import. Assert measured values and source hashes, not only that byte counts are nonzero.

For new reduction/rig code add a calibrated humanoid proxy with offset/rotated head frame, semantic UV seams and a three-bone head/neck slice; verify expected changed-region membership, normalized deform weights, target limit and untouched mask groups. Test unreachable regional budgets, missing material/UV/head group, invalid cage, exception cleanup and source preservation. A synthetic sphere without fingers cannot validate a real character's hand reduction.

Separate host parser/mask tests, native data/bake tests, actual image inspection and target-engine playback. Record failures/unavailable tiers. SELFTEST OK text cannot replace semantic assertions or actual review. Optional native fixtures may be skipped when Blender is unavailable; they must not silently become a passed host check. Save the generated artifact and version-bound images for an authorized reviewer; a successful bridge handshake proves no rendered appearance or export compatibility.
